# 지원사업 자동 매칭 서비스 개발 계획

## 1. 프로젝트 개요

### 1.1 목적

세무법인의 기존 수임업체 DB를 기반으로 정부·지자체·유관기관의 기업 지원사업 공고를 자동으로 수집하고, 공고문 및 첨부자료의 세부 지원조건을 AI로 구조화하여 향후 수임업체와 자동 매칭할 수 있는 서비스를 구축한다.

최종 목표는 단순한 "지원사업 검색 서비스"가 아니라,

> 수임업체의 현재 기업상태와 향후 계획을 기준으로  
> 해당 기업에 적합한 지원사업을 자동으로 찾아주는 서비스

를 만드는 것이다.

### 1.2 기본 원칙

1. 기존 수임업체 DB는 변경하지 않는다.
2. 지원사업 데이터는 기존 Supabase Project 안에서 별도의 테이블 영역으로 관리한다.
3. 공고 원문과 AI가 구조화한 데이터를 분리하여 보관한다.
4. 종료된 공고도 삭제하지 않고 보관한다.
5. 공고의 수정 이력을 버전으로 관리한다.
6. 공고에 명시되지 않은 조건은 `null`로 관리한다.
7. "공고에 제한 없음이라고 명시된 경우"와 "조건을 확인할 수 없는 경우"를 구분한다.
8. AI가 판단한 내용에는 가능한 한 원문 근거를 함께 저장한다.
9. 1단계에서는 "공고 수집·문서 분석·구조화"까지만 구현한다.
10. 기업과 지원사업의 실제 매칭은 2단계에서 구현한다.

# 2. 전체 시스템 구조

최종 시스템은 다음 구조를 목표로 한다.

```text
[정부/지자체/유관기관 지원사업]

        ↓
[지원사업 API / 공고 페이지]

        ↓
[공고 수집 시스템]
  ├─ 공고 기본정보
  ├─ 공고 상세정보
  └─ 첨부파일 정보

        ↓

[첨부파일 수집]
  ├─ PDF
  ├─ HWP/HWPX
  ├─ XLSX
  └─ 기타 관련 파일

        ↓

[문서 내용 추출]

        ↓

[AI 공고문 분석]
  ├─ 지원대상
  ├─ 지원자격
  ├─ 제외조건
  ├─ 우대조건
  ├─ 지역
  ├─ 업종
  ├─ 업력
  ├─ 매출
  ├─ 고용인원
  ├─ 지원내용
  ├─ 신청기간
  ├─ 필요서류
  └─ 기타 조건

        ↓

[Supabase / PostgreSQL]
  ├─ 원문
  ├─ 첨부파일
  ├─ 구조화 데이터
  ├─ 버전
  └─ 분석 근거

        ↓

============================
2단계
기업 DB ↔ 지원사업 DB 매칭
============================

        ↓

============================
3단계
웹페이지에서 추천 결과 제공
============================

        ↓

============================
4단계
담당자/고객 알림 자동화
============================
```

# 3. 단계별 개발 계획

## Phase 1. 지원사업 수집 및 AI 구조화

### 목표

기업마당을 시작점으로 지원사업 공고를 자동으로 수집하고, 공고 상세정보와 첨부자료를 분석하여 향후 매칭 가능한 구조로 Supabase에 저장한다.

### 범위

- 기업마당 API 연결
- 공고 목록 수집
- 신규/기존/수정 공고 판별
- 공고 상세정보 수집
- 첨부파일 목록 확인
- 지원자격·제외조건 등 판단에 필요한 첨부파일 다운로드
- PDF/HWP/HWPX 등 문서 내용 추출
- AI 구조화
- 원문 및 구조화 결과 저장
- 공고 버전 관리
- 분석 실패 및 오류 로그
- 향후 매칭을 고려한 데이터 구조 설계

### 1차 데이터 출처

가장 먼저 기업마당을 사용한다.

단, 데이터베이스 스키마는 향후 다음과 같은 다른 출처를 추가할 수 있도록 범용적으로 설계한다.

- K-Startup
- IRIS
- 보조금통합포털
- 중앙부처
- 광역지자체
- 기초지자체
- 지역 테크노파크 및 유관기관
- 기타 공공기관

### Phase 1에서 하지 않는 것

- 기업과 지원사업의 실제 매칭
- 적합도 점수 계산
- 고객에게 추천 알림
- 사용자용 웹페이지
- 카카오톡/문자/이메일 자동 발송

### 완료 기준

다음이 모두 충족되면 Phase 1 완료로 본다.

- [ ] 기업마당에서 공고를 자동으로 가져올 수 있다.
- [ ] 동일 공고가 중복 저장되지 않는다.
- [ ] 기존 공고가 수정되었는지 확인할 수 있다.
- [ ] 수정된 공고는 버전별로 추적할 수 있다.
- [ ] 공고에 연결된 관련 첨부파일을 가져올 수 있다.
- [ ] PDF 등 주요 문서 형식에서 내용을 추출할 수 있다.
- [ ] AI가 정해진 스키마에 따라 공고를 구조화한다.
- [ ] 알 수 없는 조건은 `null`로 저장한다.
- [ ] "제한 없음"과 "확인되지 않음"을 구분한다.
- [ ] AI 분석 결과에 가능한 경우 원문 근거가 남는다.
- [ ] Supabase에 구조화된 지원사업 데이터가 저장된다.
- [ ] 기존 수임업체 관련 테이블이 변경되지 않는다.
- [ ] 오류 발생 시 로그를 남긴다.
- [ ] 최소 1건 이상의 실제 공고를 처음부터 끝까지 자동 처리할 수 있다.

# Phase 1-A. 기존 Supabase 스키마 확인

## 목적

기존 수임업체 DB를 임의로 수정하지 않고, 향후 Phase 2에서 기업 데이터와 지원사업 데이터를 연결할 수 있도록 현재 데이터 구조를 이해한다.

### 해야 할 일

- 기존 모든 테이블 및 컬럼 확인
- 실제 운영 테이블과 백업 테이블 구분
- `client_id`를 중심으로 기업 정보 관계 파악
- 업종 관련 테이블 확인
- 기업 기본정보 테이블 확인
- 담당자 관련 테이블 확인
- 실제 매칭에 사용할 수 있는 필드 확인

### 현재 확인된 내용

현재 DB에는 다음과 같은 업종 관련 컬럼이 존재한다.

- `biz_type`
- `biz_item`
- `industry_code`

현재의 `industry_code`는 국세청 업종코드이며, 지원사업 매칭에 사용하기 위해서는 향후 한국표준산업분류(KSIC)와 연결할 필요가 있다.

### 주의

현재 운영 DB의 `industry_code` 자체를 KSIC 코드로 덮어쓰지 않는다.

---

# Phase 1-B. 국세청 업종코드와 KSIC 연결 준비

## 목적

현재 수임업체 데이터의 국세청 업종코드를 향후 지원사업의 한국표준산업분류(KSIC) 조건과 비교할 수 있도록 한다.

### 권장 구조

기존 기업 테이블은 변경하지 않고 별도의 매핑 테이블을 만든다.

예시:

```text
tax_industry_code_mapping

- tax_industry_code
- ksic_code
- ksic_level
- ksic_name
- mapping_confidence
- mapping_source
- note
```

### 원칙

- 하나의 국세청 코드가 하나의 KSIC에만 대응한다고 가정하지 않는다.
- 필요할 경우 하나의 국세청 코드에 복수 KSIC 매핑을 허용한다.
- AI가 임의로 업종코드를 변환하지 않는다.
- 공식 또는 신뢰할 수 있는 매핑 근거를 저장한다.
- 실제 매칭 로직은 Phase 2에서 구현한다.

### Phase 1 완료 범위

Phase 1에서는 매핑 테이블 구조를 준비하는 것까지로 하고, 대량 코드 매핑 및 정밀 매칭은 이후 별도로 진행한다.

# Phase 1-D. 공고 수집

## 기본 원칙

공고는 삭제하지 않는다.

- 신규 공고 → 저장
- 기존 공고 → 변경 여부 확인
- 내용 동일 → 재분석하지 않음
- 내용 변경 → 새 버전 생성 및 재분석
- 신청기간 종료 → `status`를 마감으로 변경
- 예정 공고 → 예정 상태로 관리

### 공고 상태 예시

```text
scheduled
open
closed
cancelled
unknown
```

### 중복 판별

가능하면 원본 사이트에서 제공하는 고유 공고 ID를 사용한다.

추가로 다음 정보를 이용하여 중복 여부를 보조 검증한다.

- source
- source_program_id
- title
- organization
- published_at
- original_url
- content_hash

# Phase 1-E. 공고문 및 첨부파일 수집

## 핵심 원칙

API에서 받은 공고 기본정보만으로 AI 분석을 끝내지 않는다.

지원자격, 제외업종, 세부 조건 등이 첨부파일에 있을 수 있으므로 관련 첨부자료를 함께 분석한다.

### 우선 처리 문서

1. PDF
2. HWP/HWPX
3. XLSX/XLS
4. DOCX/DOC
5. ZIP 안의 관련 문서

### 처리 절차

```text
공고 수집
  ↓
첨부파일 확인
  ↓
관련 문서 판별
  ↓
문서 다운로드
  ↓
내용 추출
  ↓
AI 분석
```

### 원칙

- 모든 첨부파일을 무조건 AI에 전달하지 않는다.
- 파일명과 공고 메타정보를 이용해 관련 파일을 우선 선별한다.
- 지원대상/자격/제외조건/신청방법/지원내용이 담긴 문서는 우선 분석한다.
- 파일 다운로드 실패 여부를 기록한다.
- 문서가 암호화되었거나 읽을 수 없는 경우 오류 상태를 저장한다.

# Phase 1-F. AI 공고문 구조화

## 목적

지원사업 공고를 사람이 읽는 문장이 아니라, PostgreSQL에서 비교하고 향후 AI 매칭에 사용할 수 있는 정형 데이터로 변환한다.

## 기본 구조

```text
program
├─ 기본정보
├─ 지원대상
├─ 자격조건
├─ 지역조건
├─ 업종조건
├─ 기업규모
├─ 업력
├─ 매출
├─ 인원
├─ 대표자 조건
├─ 인증 조건
├─ 우대조건
├─ 제외조건
├─ 중복수혜 조건
├─ 지원내용
├─ 지원금
├─ 자부담
├─ 신청기간
├─ 신청방법
├─ 필요서류
├─ 사업목적
└─ 원문 근거
```

## 반드시 지켜야 할 원칙

### 1. 추측 금지

공고문에 없는 조건은 임의로 생성하지 않는다.

### 2. `null` 사용

조건을 확인할 수 없으면 `null`로 저장한다.

예:

```json
{
  "min_revenue": null,
  "max_revenue": null
}
```

### 3. "제한 없음" 구분

공고문에 명시적으로 제한이 없다고 적혀 있는 경우와 정보가 없는 경우를 구분한다.

예:

```json
{
  "revenue_condition": {
    "status": "unlimited"
  }
}
```

vs.

```json
{
  "revenue_condition": {
    "status": "unknown",
    "min": null,
    "max": null
  }
}
```

### 4. 필수조건과 우대조건 분리

다음은 반드시 분리한다.

```text
required_conditions
preferred_conditions
excluded_conditions
```

### 5. 근거 저장

AI가 판단한 중요한 조건에는 가능한 경우 다음 정보를 저장한다.

```text
field
value
source_document
page
quote_or_evidence
```

긴 원문 전체를 복제하지 않고 판단에 필요한 짧은 근거를 저장한다.

# Phase 1-G. 구조화 데이터의 초기 JSON 형태

초기에는 사업마다 다른 조건을 수용하기 위해 JSONB 활용을 적극적으로 사용한다.

예시:

```json
{
  "target": {
    "business_types": ["법인", "개인사업자"],
    "regions": ["경기도"],
    "industry_codes": [],
    "company_size": ["중소기업"]
  },
  "eligibility": {
    "min_business_age_years": null,
    "max_business_age_years": null,
    "min_revenue": null,
    "max_revenue": null,
    "min_employee_count": null,
    "max_employee_count": null
  },
  "required_conditions": [],
  "preferred_conditions": [],
  "excluded_conditions": [],
  "duplicate_benefit_restrictions": [],
  "benefit": {
    "type": [],
    "max_amount": null,
    "support_rate": null,
    "self_payment_rate": null
  },
  "application": {
    "start_date": null,
    "end_date": null,
    "method": null
  },
  "required_documents": [],
  "business_purpose": null,
  "evidence": []
}
```

실제 운영 과정에서 자주 검색되는 조건은 나중에 별도 컬럼으로 승격할 수 있다.

# Phase 1-H. 원문과 AI 결과의 분리

다음 세 종류를 명확히 구분한다.

## 1. 원문

정부/기관에서 가져온 실제 데이터.

## 2. 구조화 결과

AI가 원문에서 추출한 데이터.

## 3. 판단 근거

AI가 어떤 문장을 근거로 특정 값을 만들었는지에 대한 정보.

AI 결과가 잘못되었을 때 원문까지 거슬러 올라갈 수 있어야 한다.

# Phase 1-I. 버전 관리

지원사업 공고는 수정될 수 있으므로 현재 데이터와 과거 데이터를 모두 보관한다.

예:

```text
공고 A

Version 1
신청기간: 8/1 ~ 8/20

Version 2
신청기간: 8/1 ~ 8/25

Version 3
지원금 수정
```

### 버전 생성 기준

내용에 실질적 변경이 있으면 새 버전을 생성한다.

단순 수집시간 변경 등 의미 없는 변경은 새 버전을 만들지 않는다.

### 비교 방법

가능하면 `content_hash`를 사용한다.

# Phase 1-J. AI 비용 및 성능 관리

모든 공고를 매일 무조건 다시 AI 분석하지 않는다.

### 처리 규칙

```text
신규 공고
→ AI 분석

기존 공고 + 내용 동일
→ 기존 결과 사용

기존 공고 + 내용 변경
→ 새 버전 생성 + AI 재분석
```

이렇게 하여 비용을 줄인다.

```text
step
error_type

created_at
```

재처리할 수 있도록 상태값도 관리한다.

# Phase 1-L. 테스트

처음부터 대량 공고를 처리하지 않는다.

## 1차 테스트

실제 공고 1건

```text
API 수집
→ 상세 확인
→ 첨부파일 다운로드
→ 문서 추출
→ AI 구조화
→ Supabase 저장
```

전체 흐름이 성공하는지 확인한다.

## 2차 테스트

서로 다른 유형의 공고 5~10건

- 첨부 PDF 중심 공고
- HWP/HWPX 중심 공고
- 첨부파일이 여러 개인 공고
- 지역사업
- 중앙부처 사업
- 업종 제한이 있는 사업
- 우대조건이 많은 사업
- 제외조건이 많은 사업

## 3차 테스트

일정 기간 동안 실제 신규 공고를 자동 수집하여 안정성을 확인한다.

# Phase 1-M. 보안 원칙

기존 수임업체 데이터는 민감한 내부 데이터이므로 지원사업 수집 시스템과 접근 권한을 분리한다.

### 원칙

- 기존 회사/수임업체 테이블을 임의로 변경하지 않는다.
- 기존 테이블 삭제 금지.
- 기존 컬럼 수정 금지.
- 기존 RLS 정책 수정 금지.
- API Key 및 Supabase Secret을 코드에 직접 입력하지 않는다.
- `.env` 및 Secret 관리 방식을 사용한다.
- 로그에 사업자번호, 고객명 등 민감정보를 불필요하게 남기지 않는다.
- 지원사업 공개 데이터와 내부 고객 데이터를 외부 AI 요청에 함께 전달하지 않는다.

# Phase 2. 기업 ↔ 지원사업 매칭

## 목표

Phase 1에서 구조화한 지원사업 조건과 기존 수임업체 데이터를 비교하여 지원 가능성이 높은 사업을 자동으로 선별한다.

## 기본 매칭 순서

```text
기업 DB
  ↓
명확한 자격조건 필터
  ↓
1차 후보사업
  ↓
AI 정밀 판단
  ↓
매칭 결과
```

## 1차 DB 필터

예:

- 지역
- 기업 형태
- 업종
- 업력
- 매출
- 직원 수

## 2차 AI 판단

예:

- 사업 목적과 기업 사업내용의 연관성
- 디지털 전환 여부
- 친환경 사업 해당 가능성
- 사업 추진계획과 지원사업 목적의 적합성

## 결과

예:

```text
company_id
program_id
eligibility
score
recommendation_level
reasons
warnings
matched_at
```

# Phase 4. 자동 알림

## 목표

새로운 지원사업이 발견되고 특정 수임업체와 매칭되면 담당자에게 자동으로 알린다.

## 가능한 채널

- 웹 알림
- 이메일
- 카카오톡
- 문자
- 내부 업무 알림

## 알림 원칙

모든 사업을 보내지 않는다.

예:

```text
적합도 90점 이상
→ 적극 추천

80~89점
→ 검토 추천

80점 미만
→ 기본적으로 알림하지 않음
```

정확한 점수 기준은 실제 운영 데이터로 조정한다.

# 5. 개발 단계 진행 원칙

각 Phase가 완료되기 전에는 다음 Phase를 본격적으로 구현하지 않는다.

특히 Phase 1에서 아래가 정상적으로 작동하지 않는 상태에서 매칭 기능을 먼저 만들지 않는다.

# 6. MVP의 가장 중요한 성공 기준

이 프로젝트의 첫 번째 성공 기준은 "많은 공고를 가져오는 것"이 아니다.

다음 질문에 제대로 답할 수 있어야 한다.

> "공고문과 첨부자료를 AI가 읽고, 사람이 매칭에 사용할 수 있는 수준으로 지원자격과 제외조건을 정확하게 구조화했는가?"

이를 검증한 이후에 기업 매칭을 구현한다.

# 7. 개발 시 항상 유지해야 할 원칙

1. 기존 수임업체 DB를 보호한다.
2. 지원사업 데이터를 독립적인 테이블 영역으로 만든다.
3. 공개 데이터와 내부 고객 데이터를 논리적으로 분리한다.
4. 공고 원문을 보존한다.
5. AI 구조화 결과를 보존한다.
6. AI 판단 근거를 보존한다.
7. 과거 공고를 삭제하지 않는다.
8. 수정 공고는 버전으로 관리한다.
9. 확인되지 않은 정보는 추측하지 않는다.
10. `null`과 "제한 없음"을 구분한다.
11. 필수조건과 우대조건을 구분한다.
12. AI 결과만 믿지 않고 원문으로 추적 가능하게 만든다.
13. 모든 자동화 작업에 재처리 가능성을 고려한다.
14. 1건의 실제 공고로 먼저 검증한다.
15. 작은 단위로 구현하고 테스트한 뒤 다음 단계로 넘어간다.
