## 이 문서 사용법

1. **작업을 시작할 때 이 문서를 먼저 읽는다.** (`CLAUDE.md`가 이 파일을 가리킨다)
2. 작업이 끝나면 해당 항목의 체크박스를 갱신하고, **완료일과 근거**(커밋 해시·파일 경로)를 적는다.
3. 작업 중 새로 확인된 사실은 [§7 실측 기록](#7-실측-기록)에 추가한다. 추측은 적지 않는다.
4. 계획이 바뀌면 항목을 지우지 말고 `[-]`로 바꾸고 **왜 접었는지** 남긴다.

## 1. 절대 어기지 않을 원칙

이 원칙을 깨는 변경은 아무리 정확도가 올라가도 채택하지 않는다.

- [ ] **확실하지 않으면 제외하지 않는다.** 자격 없는 공고를 지우는 것보다, 자격 있는 공고를 잘못 지우는 쪽이 훨씬 나쁘다. 제외(`score 0`)는 지역·시·군처럼 **확정 가능한 축**에서만. 나머지는 감점 + 주의 표시.
- [ ] **`geo.ts`는 지역 판정의 단일 출처.** 세 번째 복제본을 만들지 않는다. (이미 앱/스크립트 2벌이라 `syncParity` 테스트로 묶어둔 상태)
- [ ] **`clients` 테이블은 RLS 전잠금 유지.** 컬럼·정책 수정 금지. 접근은 Edge Function 경유만.
- [ ] **고객사 데이터를 외부 AI에 보내지 않는다.** AI에는 공개 데이터(공고문)만 전달한다.
- [ ] **`npm test`는 배포 게이트로 유지.** 새 데이터가 불변식을 깨면 배포가 막혀야 한다.
- [ ] **`null`과 "제한 없음"을 구분한다.** "조건이 없다"와 "조건을 못 읽었다"는 다른 정보다.
- [ ] **AI 판단에는 원문 근거를 함께 저장한다.** 틀렸을 때 원문까지 거슬러 갈 수 있어야 한다.

#### 설계에 반영할 결론

1. **파일명으로 선별하지 않는다.** 「공고문」 파일명만 고르면 자격조건 확보 공고가
   81건 → 60건으로 **21건(26%) 줄어든다.** 추출은 싸고 AI가 비싸므로
   **전부 추출한 뒤 내용(자격 단서)으로 거른다.** → A-2·A-3에 반영
2. **확장자를 믿지 않는다.** 223개 중 **4개가 확장자와 실제 형식이 달랐다**
   (`.hwpx`·`.xls`인데 실제로는 HWP 5.0). 매직 바이트로 판별해야 한다. → A-3에 반영
3. **자격조건의 64%가 표 안에 있다.** 평문 추출로는 구조가 뭉개진다.
   AI 프롬프트가 표 깨진 텍스트를 다루도록 설계하거나, 표를 살리는 추출이 필요하다.
4. **19%는 첨부로도 자격을 읽을 수 없다.** 스캔 PDF·포스터뿐인 공고.
   이 구간은 계속 "공고문 확인 필요"로 남는다 — 무인화 임계선의 상한이다.

### 고객사 데이터 충족률 (2026-10-27 실측)

> **C-2 의 8월 결론("업종코드뿐")을 뒤집은 측정이다.** `shared-db` 의 Supabase 를
> service_role 로 직접 조회해서 셌다.
>
> **다시 재는 법 — `node scripts/research/audit-client-data.mjs`.**
> 근로 인원은 원천세 입력이 쌓이면서 매달 올라가고 매출은 신고철마다 바뀐다.
> 이 표의 숫자를 인용하기 전에 **측정일을 먼저 본다.**

**모수 — 1,062곳.** 사업자번호가 있고 `customer_type != '해임'` 이며 `close_date` 가 없는 거래처.
매칭 앱에 로그인할 수 있는 곳과 같은 조건이다. (전체 1,751곳 · 수임상태는 기장 775 · 신고대리 636 · 해임 340)

| 값 | 채움 | 출처 |
|---|---:|---|
| `client_type` 사업자형태 | **100%** | 개인 811 · 법인 251 |
| `address` 주소 | 99.7% | 도로명(`road_address`)은 5.1%뿐 — 지번 주소로 판정 중 |
| `biz_type` 업태 / `biz_item` 종목 | 97.9% | |

| **매출액** (2025 귀속) | **82.8%** | 부가세 과표 온전 839 + 수기 보충 40. **반쪽 11곳은 뺀 수** |

**네 축(업종코드 + 업력 + 매출 + 근로자수)을 모두 갖춘 곳은 227곳(21.4%)이다.**

#### 매출 — 「온전한가」가 핵심이다

- 매출의 정의는 **부가세 과세표준 + 면세 수입금액** (2026-09-17 GH 결정, `shared-db` 20260917)
- 2025 귀속: 온전 **839** · 반쪽(있어야 할 반기가 빔) **11** · 수기 보충 **40**
- ⚠ **10-26 에 적었던 「온전 763 · 반쪽 87」은 틀린 수였다.** 그날 판정이 거칠어서
  1기·2기가 다 있는지만 봤다. 제대로 된 규칙(아래)을 넣으니 반쪽은 **11곳**으로 줄었다.
  - **간이과세자는 연 1건이 정상**이다 — 부가가치세법 제5조 제1항 제1호(과세기간 1/1~12/31).
    모수에 간이 60 + 간이(계산서) 23 = 83곳이 있어 이들이 통째로 「반쪽」에 들어가 있었다
  - **그 해 개업 전·폐업 후인 반기**는 비어 있는 게 정상이라 「빠졌다」고 세지 않는다
  - **면세는 연 1건**이되, 겸영(과세+면세)이면 부가세 반기도 봐야 한다
  - 귀속을 아직 안 고른 줄(`period_chosen = false`)은 뺀다
- **2024년 이전은 1곳뿐이다.** 직전연도 조건을 2025로 읽는 지금은 되지만, 해가 바뀌면 다시 센다
- 금액 분포(온전한 839곳): 1억 미만 475 · 1~5억 242 · 5~10억 59 · 10~50억 54 · 50억+ 9.
  **중앙값 0.61억 · 최대 240.5억 · 0원 115곳**
- ⚠ 반쪽을 온전한 값처럼 쓰면 「매출 10억 미만」 판정이 그대로 틀린다.
  dh-platform `src/lib/filings.ts` 의 `incomeCoverageMap()` 이 `none/partial/full` 을 이미 낸다.
  `audit-client-data.mjs` 의 판정은 **그 함수를 옮겨 적은 것**이다 — 어긋나면 dh-platform 쪽이 맞다

#### 근로자수 — 왜 25.5%인가

```
1,062곳
├ 680곳  원천세 신고 행 있음 (64.0%)
│  ├ 271곳  근로 인원 입력됨 (행 있는 곳의 39.9%)  ← 쓸 수 있는 것
│  └ 409곳  행은 있는데 인원 칸이 빔              ← 입력 공백
└ 382곳  원천세 행 자체가 없음
   └ 신고대리 236 · 기장 73 · 신고행 없음 73   ← 모르는 것이지 0명이 아니다
```

- **입력이 달마다 늘고 있다** — 1월 130 · 2월 115 · 3월 112 · 4월 121 · 5월 103 ·
  6월 149 · 7월 133 · 8월 182 · **9월 234** · 10월 21(진행 중)
- 2025년은 **0건**. 담당자별 엑셀 이관이 2026년분만 됐다
- 인원 분포(최댓값 기준): 1~4명 217 · 5~9명 31 · 10~49명 21 · 50명+ 1. **중앙값 2명**
- 곁가지: 일용직 인원 56곳 · 사업소득 인원 270곳. `filing_yearend`(연말정산)는 **0행**
- 3개월 이상 기록이 쌓인 곳은 **145곳**뿐이다. 「상시」 근로자를 말하려면 몇 달치가 필요한데,
  한 달치만 있는 126곳은 그 달 숫자를 그대로 쓸 수밖에 없다

#### 업종코드는 채워져 있어도 바로 못 쓴다 🔴

공고문의 업종 제한은 **통계청 표준산업분류(5자리)**, `clients.industry_code` 는
**국세청 업종코드(6자리)**다. 코드끼리 맞출 수가 없다.
`shared-db` `20260917_voucher_overrides.sql` 에 이 문제에 부딪힌 기록이 있고,
dh-platform 은 **업태·종목 이름으로 후보만 좁혀 「확인필요」로 두고 사람이 정하는** 길을 택했다.

#### 이미 같은 일을 하는 화면이 있다

`dh-platform` 의 **「지원사업」 화면**(`src/app/.../support/[program]`)이 2026년 소상공인 바우처를
자동 판정하고 있다. 「자료없음」 카드에서 매출을 직접 입력받고, 담당자가 손으로 바로잡은 결과를
`voucher_overrides` 에 쌓는다. `src/lib/sincere.ts` 는 성실신고 기준으로 업종을 3그룹으로 가른다.

**매칭 앱과 별개로 같은 판정을 하고 있다.** A-6·C-7 에 들어가기 전에 이쪽 로직을 먼저 읽을 것 —
매출 집계 · 업종 판정 · 「확인필요」 처리가 이미 실무에서 검증됐다.

### 기존 시스템에서 실측으로 얻은 판정 규칙

**AI 구조화로 바꿔도 같은 함정이 존재한다.** 프롬프트에 명시할 것.

| 규칙 | 근거 |
|---|---|
| 전국 공고 임계값 **13개 시도** | 기업마당은 전국 사업 해시태그에 17개 시도를 전부 나열. 실측 분포가 1~6개 → 13개 이상으로 끊김 |
| 나열형 배제 | "지식서비스산업, 문화콘텐츠산업, 벤처기업 **등**", "소상공인 **또는** 여성기업" → 전용 조건 아님 |
| 자격 문단만 읽기 | '여성' 언급 31건 중 **대표자 조건은 13건.** 나머지는 "여성기업 우대" 한 줄 |
| 태그 시·군 3개 이상은 무시 | 3개 이상 나열되면 특정 시·군 전용이 아니라 광역 사업 |

| 방산은 규칙에 넣지 않음 | 업태·종목으로 식별 불가(해당 고객사 0개사) → 전 고객사 오탐 |
