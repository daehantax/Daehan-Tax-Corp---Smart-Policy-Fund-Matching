# 지원사업 매칭 고도화 작업계획서

> **최종 목표** — 수임업체의 기업 상태를 기준으로 최적의 지원사업을 자동 선별하여,
> 사람의 개입 없이 컨설팅 수준의 추천을 제공한다.
>
> 이 문서는 기존 운영 시스템(`policy_grants` 기반 매칭)과 신규 설계
> ([`docs/PROJECT_PLAN.md`](PROJECT_PLAN.md), 첨부파일 수집 + AI 구조화)를 통합한
> **단일 작업 기준**이다.

---

## 이 문서 사용법

1. **작업을 시작할 때 이 문서를 먼저 읽는다.** (`CLAUDE.md`가 이 파일을 가리킨다)
2. 작업이 끝나면 해당 항목의 체크박스를 갱신하고, **완료일과 근거**(커밋 해시·파일 경로)를 적는다.
3. 작업 중 새로 확인된 사실은 [§7 실측 기록](#7-실측-기록)에 추가한다. 추측은 적지 않는다.
4. 계획이 바뀌면 항목을 지우지 말고 `[-]`로 바꾸고 **왜 접었는지** 남긴다.

### 상태 표기

| 표기 | 뜻 |
|---|---|
| `[ ]` | 미착수 |
| `[~]` | 진행 중 |

## 0. 현재 위치

기존 시스템과 신규 계획서를 대조한 결과, **둘은 같은 파이프라인의 서로 다른 절반**이다.

```
공고수집 → 첨부수집 → 문서추출 → AI구조화 → DB → 매칭 → 웹 → 알림
└─────┘   └──────────────────────────────┘   └──────────────┘
 있음         전부 없음 ← 이번 작업 범위        이미 운영 중
```

| | 상태 |
|---|---|
| 이미 운영 중 | 매칭 점수, 지역·시군 판정, 고객사 2단계 인증, 웹서비스(`fund.daehantax.com`), 회귀 테스트 5종 |
| 비어 있음 | 첨부파일 수집, 문서 추출, AI 구조화, 버전 관리, 판단 근거, 오류 재처리, KSIC 매핑 |
| **진짜 병목** | **기업 쪽 데이터 부족** — 2026-08-20 확인: 매출·근로자수는 컬럼조차 없고 개업일자는 값이 비어 있다. 공고를 완벽히 읽어도 대조할 값이 없다 → §4-1 |

### 접근 방식

기존 `policy_grants`와 서비스는 **건드리지 않고**, 신규 테이블을 나란히 만들어
검증이 끝난 뒤 **자격 조건의 출처만 교체**한다. 서비스 무중단, 되돌리기 비용 최소.

## 1. 절대 어기지 않을 원칙

이 원칙을 깨는 변경은 아무리 정확도가 올라가도 채택하지 않는다.

- [ ] **확실하지 않으면 제외하지 않는다.** 자격 없는 공고를 지우는 것보다, 자격 있는 공고를 잘못 지우는 쪽이 훨씬 나쁘다. 제외(`score 0`)는 지역·시·군처럼 **확정 가능한 축**에서만. 나머지는 감점 + 주의 표시.
- [ ] **`geo.ts`는 지역 판정의 단일 출처.** 세 번째 복제본을 만들지 않는다. (이미 앱/스크립트 2벌이라 `syncParity` 테스트로 묶어둔 상태)
- [ ] **`clients` 테이블은 RLS 전잠금 유지.** 컬럼·정책 수정 금지. 접근은 Edge Function 경유만.
- [ ] **고객사 데이터를 외부 AI에 보내지 않는다.** AI에는 공개 데이터(공고문)만 전달한다.
- [ ] **`npm test`는 배포 게이트로 유지.** 새 데이터가 불변식을 깨면 배포가 막혀야 한다.
- [ ] **`null`과 "제한 없음"을 구분한다.** "조건이 없다"와 "조건을 못 읽었다"는 다른 정보다.
- [ ] **AI 판단에는 원문 근거를 함께 저장한다.** 틀렸을 때 원문까지 거슬러 갈 수 있어야 한다.

#### 핵심 결과

| 지표 | 값 |
|---|---:|
| 표본 공고 / 첨부파일 | 100건 / 223개 (공고당 2.2개) |
| **자격조건을 첨부에서 읽을 수 있는 공고** | **81 / 100 (81%)** |
| 텍스트 추출 성공 | 189 / 223개 |
| HWP·HWPX 추출 성공률 | **100%** (한글 라이선스 불필요) |
| PDF 추출 성공률 | 79.5% — 실패는 대부분 포스터·리플렛 |
| 스캔 이미지 PDF | 16 / 78 (20.5%) |
| 표 포함 문서 | 121 / 189 (64%) |
| 제외 조건 문구가 있는 공고 | 71 / 100 (71%) |
| AI 투입 분량 (내용 선별 후) | 공고당 평균 **9,709자** |

#### 설계에 반영할 결론

1. **파일명으로 선별하지 않는다.** 「공고문」 파일명만 고르면 자격조건 확보 공고가
   81건 → 60건으로 **21건(26%) 줄어든다.** 추출은 싸고 AI가 비싸므로
   **전부 추출한 뒤 내용(자격 단서)으로 거른다.** → A-2·A-3에 반영
2. **확장자를 믿지 않는다.** 223개 중 **4개가 확장자와 실제 형식이 달랐다**
   (`.hwpx`·`.xls`인데 실제로는 HWP 5.0). 매직 바이트로 판별해야 한다. → A-3에 반영
3. **자격조건의 64%가 표 안에 있다.** 평문 추출로는 구조가 뭉개진다.
   AI 프롬프트가 표 깨진 텍스트를 다루도록 설계하거나, 표를 살리는 추출이 필요하다.
4. **19%는 첨부로도 자격을 읽을 수 없다.** 스캔 PDF·포스터뿐인 공고.
   이 구간은 계속 "공고문 확인 필요"로 남는다 — 무인화 임계선의 상한이다.

## 4-1. 기업 데이터 준비 — 별도 트랙 🔴

> C-2에서 드러난 것: **권한은 있는데 데이터가 없다.**
> 공고를 아무리 잘 읽어도 대조할 값이 없으면 매칭이 안 된다.
> 이 트랙은 `shared-db` 쪽 작업이라 이 저장소 범위 밖이지만,
> **M-4(수치 조건 판정)가 여기에 전적으로 종속**되므로 함께 관리한다.

우선순위는 공고 출현율 순이다. 매출액 하나가 나머지를 합친 것보다 크다.

- [ ] **D-1. 매출액** (공고 60%) 🔴 최우선
  - `clients`에 컬럼 추가 + 값 적재
  - **구간값으로 저장할지, 원본을 저장하고 조회 시 구간으로 변환할지 결정**
    (원본 저장 + 서버에서 구간 변환이 유연하지만, 원본이 DB에 남는다)
  - 기준 연도 정의 — 직전 사업연도인가, 최근 12개월인가
  - 신규·휴업 등 매출이 없는 경우의 표현 (`null` vs `0`)
- [ ] **D-2. 상시근로자수** (공고 23%)
  - `clients`에 컬럼 추가 + 값 적재. 집계 인원수만
  - 기준 시점 정의 (연평균 / 특정 월 말)
- [ ] **D-3. 개업일자 값 채우기** (공고 14%)
  - 컬럼은 이미 있고 **값이 비어 있다.** 신규 컬럼보다 쉬운 작업
  - 업력 = 공고 기준일 − 개업일자로 계산 (저장은 개업일자만)
- [ ] **D-4. 갱신 주기 결정**
  - 매출·근로자수는 시간이 지나면 틀려진다. 언제 다시 채우는가
  - 값이 오래되면 "확인 필요"로 떨어뜨릴 기준일 설정

**진행을 막지 않는 것** — Phase 1(수집)·Phase 2(AI 구조화)는 이 트랙과 무관하게 진행한다.
공고에서 조건을 뽑는 일은 우리 쪽 데이터와 상관없다. 종속되는 건 M-4(판정)뿐이다.

**먼저 쓸 수 있는 것** — `industry_code`는 이미 채워져 있으므로
**업종 조건(공고 24%)은 데이터 준비 없이 바로 갈 수 있다.** C-7 → A-10 → M-4 순서로.

| 전국 공고 임계값 **13개 시도** | 기업마당은 전국 사업 해시태그에 17개 시도를 전부 나열. 실측 분포가 1~6개 → 13개 이상으로 끊김 |
| 나열형 배제 | "지식서비스산업, 문화콘텐츠산업, 벤처기업 **등**", "소상공인 **또는** 여성기업" → 전용 조건 아님 |
| 자격 문단만 읽기 | '여성' 언급 31건 중 **대표자 조건은 13건.** 나머지는 "여성기업 우대" 한 줄 |
| 태그 시·군 3개 이상은 무시 | 3개 이상 나열되면 특정 시·군 전용이 아니라 광역 사업 |
| 2글자 자치구는 태그에서 제외 | "강소특구" → '서구'로 오탐 |
| 방산은 규칙에 넣지 않음 | 업태·종목으로 식별 불가(해당 고객사 0개사) → 전 고객사 오탐 |
