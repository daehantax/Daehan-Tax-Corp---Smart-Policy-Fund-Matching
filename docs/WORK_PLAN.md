# 지원사업 매칭 고도화 작업계획서

> **최종 목표** — 수임업체의 기업 상태를 기준으로 최적의 지원사업을 자동 선별하여,
> 사람의 개입 없이 컨설팅 수준의 추천을 제공한다.
>
> 이 문서는 기존 운영 시스템(`policy_grants` 기반 매칭)과 신규 설계
> ([`docs/PROJECT_PLAN.md`](PROJECT_PLAN.md), 첨부파일 수집 + AI 구조화)를 통합한
> **단일 작업 기준**이다.

---

## 이 문서 사용법

1. **작업을 시작할 때 이 문서를 먼저 읽는다.** (`CLAUDE.md`가 이 파일을 가리킨다)
2. 작업이 끝나면 해당 항목의 체크박스를 갱신하고, **완료일과 근거**(커밋 해시·파일 경로)를 적는다.
3. 작업 중 새로 확인된 사실은 [§7 실측 기록](#7-실측-기록)에 추가한다. 추측은 적지 않는다.
4. 계획이 바뀌면 항목을 지우지 말고 `[-]`로 바꾸고 **왜 접었는지** 남긴다.

### 상태 표기

| 표기 | 뜻 |
|---|---|
| `[ ]` | 미착수 |
| `[~]` | 진행 중 |
| `[x]` | 완료 |
| `[!]` | 막힘 — 사유 필수 |
| `[-]` | 보류·취소 — 사유 필수 |

## 0. 현재 위치

기존 시스템과 신규 계획서를 대조한 결과, **둘은 같은 파이프라인의 서로 다른 절반**이다.

```
공고수집 → 첨부수집 → 문서추출 → AI구조화 → DB → 매칭 → 웹 → 알림
└─────┘   └──────────────────────────────┘   └──────────────┘
 있음         전부 없음 ← 이번 작업 범위        이미 운영 중
```

| | 상태 |
|---|---|
| 이미 운영 중 | 매칭 점수, 지역·시군 판정, 고객사 2단계 인증, 웹서비스(`fund.daehantax.com`), 회귀 테스트 5종 |
| 비어 있음 | 첨부파일 수집, 문서 추출, AI 구조화, 버전 관리, 판단 근거, 오류 재처리, KSIC 매핑 |
| **진짜 병목** | **기업 쪽 데이터 부족** — 공고를 완벽히 읽어도 우리 DB에 업력·매출·근로자수가 없으면 매칭 불가 |

### 접근 방식

기존 `policy_grants`와 서비스는 **건드리지 않고**, 신규 테이블을 나란히 만들어
검증이 끝난 뒤 **자격 조건의 출처만 교체**한다. 서비스 무중단, 되돌리기 비용 최소.

## 1. 절대 어기지 않을 원칙

이 원칙을 깨는 변경은 아무리 정확도가 올라가도 채택하지 않는다.

- [ ] **확실하지 않으면 제외하지 않는다.** 자격 없는 공고를 지우는 것보다, 자격 있는 공고를 잘못 지우는 쪽이 훨씬 나쁘다. 제외(`score 0`)는 지역·시·군처럼 **확정 가능한 축**에서만. 나머지는 감점 + 주의 표시.
- [ ] **`geo.ts`는 지역 판정의 단일 출처.** 세 번째 복제본을 만들지 않는다. (이미 앱/스크립트 2벌이라 `syncParity` 테스트로 묶어둔 상태)
- [ ] **`clients` 테이블은 RLS 전잠금 유지.** 컬럼·정책 수정 금지. 접근은 Edge Function 경유만.
- [ ] **고객사 데이터를 외부 AI에 보내지 않는다.** AI에는 공개 데이터(공고문)만 전달한다.
- [ ] **`npm test`는 배포 게이트로 유지.** 새 데이터가 불변식을 깨면 배포가 막혀야 한다.
- [ ] **`null`과 "제한 없음"을 구분한다.** "조건이 없다"와 "조건을 못 읽었다"는 다른 정보다.
- [ ] **AI 판단에는 원문 근거를 함께 저장한다.** 틀렸을 때 원문까지 거슬러 갈 수 있어야 한다.

- [ ] 텍스트 추출 성공률 (형식별)

### C-2. 기업 쪽 데이터 가용 범위 확정 `[ ]` 🔴 **최우선 · 사장님 결정 필요**

현재 `verify-brn`이 읽는 고객사 필드는 이것이 전부다:
상호, `client_type`(법인/개인), `biz_type`(업태), `biz_item`(종목), `address`, 대표자 생년월일·성별.

**업력·매출·근로자수·인증보유는 한 건도 없다.** 공고에서 아무리 잘 뽑아도 대조할 값이 없다.

- [ ] **업력** — 개업일자를 쓸 수 있는가? 어느 테이블에 있는가?
- [ ] **매출** — 부가세·법인세 신고 데이터를 이 시스템이 참조해도 되는가?
- [ ] **근로자수** — 원천징수 이행상황신고 데이터를 쓸 수 있는가?
- [ ] **인증보유** — 벤처·이노비즈·메인비즈 등 관리하는 데이터가 있는가?
- [ ] 각 항목의 **개인정보·비밀유지 관점 사용 가능 범위** 결정
- [ ] 사용 가능으로 결정된 항목의 **조회 경로 설계** (RLS 유지 전제, Edge Function 확장)

> **이 결정이 AI 구조화 스키마의 우선순위를 정한다.**
> 못 쓰기로 한 항목은 공고에서 뽑아도 "확인 필요"로만 표시된다 — 뽑는 비용을 낮춰야 한다.

## 3. 추가해야 할 내용

### Phase 1 — 수집 기반 (매칭에 연결하지 않음)

- [ ] **A-1. 신규 테이블 생성** — `support_programs`, `support_program_attachments`, `support_program_versions`, `support_program_analysis`, `tax_industry_code_mapping`

- [ ] **A-2. 첨부파일 수집기** — `detail_url` → 상세페이지 → `atchFileId` 추출 → `fileDown.do` 다운로드
  - 경로는 검증 완료 ([§7](#7-실측-기록) 참조)
  - 신규 공고만 처리 (`pblanc_id` 기준). 매일 전수 재수집 금지
  - 다운로드 실패는 상태로 기록하고 재처리 가능하게
- [ ] **A-3. 문서 텍스트 추출기** — HWP → HWPX → PDF → XLSX 순으로 구현
  - HWP 5.0은 `olefile` + `zlib`로 검증 완료. 한글 라이선스 불필요
  - 형식별 실패는 조용히 넘기지 말고 `extracted_text_status`에 기록
- [ ] **A-7. 오류 로그 + 재처리 상태** — `source / program_id / step / error_type / error_message / created_at`
- [ ] **A-8. 버전 관리** — `content_hash` 비교, 실질 변경 시에만 새 버전

### Phase 2 — AI 구조화 + 정확도 검증

> **순서를 지킬 것.** 골든셋(A-4)이 AI(A-5)보다 먼저다.
> 정답이 없으면 프롬프트를 고쳤을 때 좋아졌는지 나빠졌는지 알 수 없다.

- [ ] **A-4. 골든셋 라벨링 (30~50건)** — 사람이 직접 정답 작성
  - 유형을 섞을 것: PDF 중심 / HWP 중심 / 첨부 다수 / 지역사업 / 중앙부처 / 업종제한 / 제외조건 다수
  - 기존 회귀 테스트와 같은 철학 — **실제로 틀렸던 지점**을 우선 채집
- [ ] **A-5. AI 구조화 파이프라인** — 계획서 Phase 1-G 스키마 기반
  - 프롬프트에 **반드시** 넣을 규칙 (기존 시스템이 실측으로 얻은 것):
    - 나열형 배제 — "A, B, C 등" / "A 또는 B"의 항목을 조건으로 승격시키지 말 것
    - 자격 문단 우선 — 본문 전체의 부수 언급("○○기업 우대")을 조건으로 삼지 말 것
    - 필수 / 우대 / 제외를 반드시 분리
    - 확인 불가는 `null`, 명시적 무제한은 `unlimited`
  - 판단마다 원문 근거(`evidence`) 저장
- [ ] **A-6. 정확도 측정 하네스** — 골든셋 대비 필드별 정확도·재현율 리포트
  - 프롬프트·모델 변경 시 반드시 재측정
  - 목표치는 C-1 조사 후 현실적으로 설정

### 첨부파일 다운로드 (2026-08-20 실측)

- **동작하는 경로**: `https://www.bizinfo.go.kr/cmm/fms/fileDown.do?atchFileId=FILE_...&fileSn=N`
  → HTTP 200, 인증·쿠키 불필요
- **404 나는 경로**: `/webapp/upload/bizinfo/file/YYYY/MM/...hwp` (페이지의 "바로보기"용)
- `atchFileId`는 상세페이지 HTML에서 추출 가능 — `detail_url`은 이미 DB에 있음

### HWP 본문 추출 (2026-08-20 실측)

- HWP 5.0 = OLE 복합문서. `olefile` + 표준 `zlib`로 `BodyText/Section*` 해제 후
  `HWPTAG_PARA_TEXT`(tag 67) 레코드만 읽으면 본문 추출됨
- **한글 라이선스·외부 서비스 불필요**
- 실측: 공고문 1건에서 **6,769자** 추출 성공. 표 안 셀 텍스트도 나옴

### 기존 시스템에서 실측으로 얻은 판정 규칙

**AI 구조화로 바꿔도 같은 함정이 존재한다.** 프롬프트에 명시할 것.

| 규칙 | 근거 |
|---|---|
| 전국 공고 임계값 **13개 시도** | 기업마당은 전국 사업 해시태그에 17개 시도를 전부 나열. 실측 분포가 1~6개 → 13개 이상으로 끊김 |
| 나열형 배제 | "지식서비스산업, 문화콘텐츠산업, 벤처기업 **등**", "소상공인 **또는** 여성기업" → 전용 조건 아님 |
| 자격 문단만 읽기 | '여성' 언급 31건 중 **대표자 조건은 13건.** 나머지는 "여성기업 우대" 한 줄 |
| 태그 시·군 3개 이상은 무시 | 3개 이상 나열되면 특정 시·군 전용이 아니라 광역 사업 |
| 2글자 자치구는 태그에서 제외 | "강소특구" → '서구'로 오탐 |
| 방산은 규칙에 넣지 않음 | 업태·종목으로 식별 불가(해당 고객사 0개사) → 전 고객사 오탐 |
